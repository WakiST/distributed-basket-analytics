# Сетевой протокол

Все TCP-сообщения - JSON в UTF-8, одно сообщение на строку (`\n`). Максимальный размер сообщения - 2 МиБ. Версия протокола - 1. Все временные метки - Unix time в секундах.

По умолчанию брокер слушает 127.0.0.1:

| Порт | Транспорт | Назначение |
|---|---|---|
| 9000 | TCP | Отправка заданий, запрос результата, мониторинг |
| 9001 | TCP | Регистрация воркеров, выдача заданий, ACK |
| 9002 | TCP | Отдельный канал подписки на изменения статуса |
| 9003 | UDP | Heartbeat воркеров |

Отдельный веб-сервер использует TCP 8088 для HTTP. Он подключается к указанному брокеру как обычный TCP-клиент, а браузеры подключаются только к веб-серверу.

## Клиент

`{"type":"submit","operation":"sum","data":[10,20],"priority":5}`

Ответ содержит `task_id` и секретный `task_token`. Их необходимо сохранить для чтения результата и подписки. Приоритет - целое число от 0 до 9; большее значение означает более срочное задание. При одинаковом приоритете действует FIFO. Уже выполняющиеся задания не вытесняются.

`{"type":"status","task_id":"…","task_token":"…"}` - текущее состояние и результат.

`{"type":"monitor"}` - очередь, состояния воркеров и счётчики заданий без секретных токенов.

## Подписки

На отдельном TCP-порту клиент передаёт `{"type":"subscribe","task_id":"…","task_token":"…","after_version":0}`. Брокер сначала отправляет сохранённые события с большей версией, затем новые события. Последовательность статусов: `queued → running → completed/error`. При повторной выдаче: `running → queued → running`. На каждый переход растёт `version`. Финальное событие содержит результат либо описание ошибки. Переподключение возможно с последней прочитанной версией; история ограничена, поэтому при пропуске старых событий клиент получает актуальное состояние.

## Воркеры

Воркер отправляет `{"type":"register","worker_id":"…","protocol":1}` и получает параметры heartbeat, UDP-порт и случайный `session_token`. Повторная регистрация уже подключённого worker_id отклоняется.

Брокер выдаёт `{"type":"task","task_id":"…","attempt_id":"…","operation":"…","data":…, "attempt":1}`. Один воркер одновременно выполняет одно задание.

После вычисления воркер отправляет `{"type":"ack","task_id":"…","attempt_id":"…","ok":true,"result":…}`; при ошибке - `ok:false,error:"…"`. ACK одновременно подтверждает окончание работы и доставляет результат. Брокер отвечает `ack_received` с полем `accepted`. ACK принимается только от текущего владельца задания и только для текущего `attempt_id`.

UDP heartbeat: `{"type":"heartbeat","worker_id":"…","session_token":"…"}`. Таймер отсчитывается по монотонным часам. Пакеты чужой или старой сессии игнорируются.

## Отказы и гарантии

При разрыве TCP, пропаже heartbeat или истечении времени выполнения брокер отключает сессию воркера и возвращает незавершённое задание в очередь. Повторная попытка сохраняет исходные приоритет и FIFO-позицию и назначается узлу с другим worker_id. Пока другого узла нет, задание ожидает в очереди; доступный воркер может выполнять следующие подходящие задания. Число попыток ограничено; после исчерпания задача переходит в `error`. Ошибки входных данных и вычислений повторно не исполняются.

Гарантия исполнения - **at least once**: при сбое одно вычисление может фактически произойти несколько раз. Внешних побочных эффектов у предусмотренных операций нет; брокер принимает только один актуальный результат.

Очередь и результаты хранятся в оперативной памяти; перезапуск брокера их сбрасывает. Протокол рассчитан на доверенную учебную локальную сеть: TLS и учётных записей нет. Токены закрывают доступ к чужому результату, но не заменяют шифрование и полноценную аутентификацию. Для работы между компьютерами брокер запускается с `--host 0.0.0.0`, клиенты и воркеры используют его LAN-адрес.

## Веб-клиент

`basketnet.web` предоставляет HTTP-интерфейс поверх существующего TCP-клиента. Вычисления выполняются только воркерами; веб-сервер их не подменяет.

| Адрес | Назначение |
|---|---|
| `GET /api/catalog` | Открытый каталог без входа |
| `GET /api/session` | Создать/восстановить сеанс, узнать пользователя и роль |
| `POST /api/auth/register`, `/api/auth/login`, `/api/auth/logout` | Регистрация, вход и выход; вход меняет cookie сеанса |
| `GET/POST /api/cart` | Собственная корзина; POST: `product_id`, `quantity` (0 удаляет) |
| `GET /api/coupons` | Личные купоны покупателя |
| `POST /api/orders` | Оформить серверную корзину: `request_key`, `coupon` |
| `GET /api/orders` | Собственная история заказов и чеков |
| `GET /api/admin/state` | Все заказы, серии и каталог для администратора |
| `POST /api/admin/generate` | Серия: `count`, `concurrency`, `load`, `priority_min`, `priority_max` |
| `POST /api/admin/stop` | Остановить подачу серии по `batch_id` |
| `POST /api/admin/product` | Изменить товар, цена в целых копейках `cents` |
| `POST /api/admin/coupon` | Выдать купон: `login`, `code`, `percent` |
| `POST /api/admin/analytics` | Аналитика магазина: `operation`, `include_generated` |
| `POST /api/tasks` | Лаборатория администратора: `operation`, `data`, `priority` |
| `GET /api/tasks/ID` | Получить текущий результат и историю своего задания |
| `GET /api/tasks/ID/handle` | Скачать ID и токен для консольного клиента |
| `GET /api/events` | Отдельный SSE-поток уведомлений всех заданий сеанса |
| `GET /api/monitor` | Состояние брокера и воркеров |

Сеанс определяется случайной cookie `basketnet_session` с `HttpOnly` и `SameSite=Strict`. Веб-клиент не помещает токены заданий в URL. Изменяющие запросы используют JSON и заголовок `X-BasketNet-Client: browser`; чужой Origin отклоняется. Аккаунты хранятся в SQLite; пароли - PBKDF2-SHA256 с индивидуальной солью, 200 000 итераций. Только администратор может обращаться к `/api/admin/*`, `/api/tasks*` и `/api/monitor`. Корзины, купоны и заказы привязаны к пользователю, которого сервер берёт из сеанса. Незнакомая cookie даёт 401, недостаточная роль - 403. После входа и выхода старый токен инвалидируется. Ограничение входа/регистрации: 15 попыток в минуту на IP.

На каждое активное задание веб-сервер открывает TCP-подписку на отдельном порту брокера. События лаборатории передаются браузеру через SSE с именами `snapshot` и `task`. Для покупателя событие `orders` передаёт актуальные собственные заказы при изменениях с интервалом проверки до секунды. При переподключении браузер получает актуальное состояние, при разрыве TCP сайт переподписывается с последней версией. Служебная строка SSE отправляется примерно раз в секунду, если нет событий лаборатории. При выходе сеанс и его поток закрываются.

Заказы последовательно проходят `sum` и `hash`. `sum` дополнительно принимает `work_iterations` от 0 до 2 000 000 для генератора: PBKDF2-SHA256 нагружает CPU, результат чека не меняется, добавляются `work_digest` и `work_iterations`. Покупатель не управляет нагрузкой и приоритетом своего заказа через HTTP. Сначала задача рассчитывает сумму и скидки, затем отдельная задача `hash` получает сериализованный документ чека. Строка `receipt_text` сохраняется и попадает в скачанный JSON как `fiscal_data`; SHA-256 вычислен именно от её UTF-8-байтов.

Лимиты генератора: 1-200 заказов, окно 1-30, одна активная серия. Сайт обслуживает до 40 параллельных заказов суммарно, остальное ожидает допуска. Окно серии включает очередь брокера и выполнение, это не число процессов-воркеров. Остановка серии отменяет только ещё не допущенные заказы. Заказы и токены этапов сохраняются в SQLite; межсистемной транзакции между SQLite и отправкой TCP нет, поэтому после аварии вычисление может повториться без создания нового заказа.

Целые числа, выходящие за безопасный диапазон JavaScript, передаются в HTTP-ответах десятичными строками. Структура результатов остальных операций сохраняется.
